# ExLab 0.5.23 — 修复 Center 历史记录增长导致的请求积压

历史实验包含大型启动脚本时，旧版 Center 在每次节点心跳中读取全部历史任务并重建耗时样本。列表刷新和规则巡检也重复读取这些脚本，巡检还逐条提交观察记录。它们占用同一调度锁，造成接口超时、重试积压以及“管理端离线”。

- 心跳通过索引选择当前任务和未确认指令。没有待分配任务、或交接仍在等待原进程停止/检查点时，不重建调度模型。
- SQLite 触发器在任务原事务内维护轻量状态。大型启动脚本、日志和诊断正文继续保存在原任务中，列表与巡检使用投影；升级首次补建已有记录。该投影随完整 Center 数据库同步。
- 列表通过独立只读连接读取一致的任务快照，在调度锁外读取、解析和整理历史记录，避免页面刷新阻塞节点心跳。事务内调用保留读取自身未提交修改的行为。
- 调度锁按等待顺序交接并支持重入，连续巡检、刷新不能越过已经等待的节点请求。
- 耗时样本使用持久化的任务身份散列，只在定义改变时失效；保留每种任务、每个节点最近十条有效样本和原有中位数估计规则。
- 规则巡检只保存变化的观察记录，批量提交发现。自动操作继续使用各自的持久化请求与权限检查。
- 本机健康检查使用独立只读数据库连接，认证不等待调度锁。HTTP 同时最多处理 64 条连接；过载时在执行操作前返回 503 和 `Retry-After: 1`。客户端断开时发送错误回复失败也会正常收尾。

实验归属、科学参数、检查点交接和待确认回报保持原协议。升级只交接 Center 管理进程，节点中的 Docker 实验继续运行。包含 0.5.22 的 Worker 网络回复截断恢复修复。Monitor APK 继续使用 0.5.22。

回归覆盖历史大脚本读取隔离、投影更新与旧库迁移、样本失效与中位数、观察记录批量提交、调度锁繁忙时的健康检查、连接上限及断线清理；另用真实数据库副本与放大历史记录进行性能验证。
